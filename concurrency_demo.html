Concurrency Control Implementation

Scenario: Product stock = 1 unit. User A and User B both click "Buy" simultaneously.

Without Transaction Control

Old implementation (UNSAFE)

User A: Check stock → stock = 1 ✓
User B: Check stock → stock = 1 ✓
User A: Reduce stock → stock = 0
User B: Reduce stock → stock = -1
User A: Create order ✓
User B: Create order ✓
Result: Both orders succeed!
Final Stock: -1
Problem: Overselling occurred - negative inventory
Code Flow:
// Step 1: Validate (no lock)
if (validate_stock($id, $qty)) {
    // Step 2: Reduce stock (separate)
    reduce_stock($id, $qty);
    
    // Step 3: Create order (separate)
    create_order($user_id);
}

Issue: Steps are not atomic. Race condition between validation and stock reduction.

With Transaction Control

New implementation (SAFE)

User A: BEGIN TRANSACTION
User A: SELECT ... FOR UPDATE (LOCKS)
User B: BEGIN TRANSACTION
User B: SELECT ... FOR UPDATE (WAITS...)
User A: Check: stock = 1 ✓
User A: UPDATE stock = 0
User A: INSERT order
User A: COMMIT (releases lock)
User B: Lock acquired! Check: stock = 0 ✗
User B: ROLLBACK (insufficient stock)
Result: Only User A's order succeeds!
Final Stock: 0
User B: Gets "Out of Stock" error
Code Flow:
// START TRANSACTION
mysqli_begin_transaction($con);

// LOCK the product row
SELECT ... FOR UPDATE;

// Check stock INSIDE transaction
if ($stock >= $qty) {
    // Reduce stock
    UPDATE products SET stock = stock - $qty;
    
    // Create order
    INSERT INTO orders ...;
    
    // COMMIT (atomic)
    mysqli_commit($con);
} else {
    // ROLLBACK
    mysqli_rollback($con);
    return error;
}

Solution: All operations are atomic. Lock prevents concurrent access.

Technical Details

SELECT ... FOR UPDATE

This SQL clause acquires an exclusive lock on the selected rows:

  • Other transactions trying to lock the same rows must wait
  • Lock is held until COMMIT or ROLLBACK
  • Prevents dirty reads and lost updates
  • Works only with InnoDB engine (which we use)
Transaction Isolation

MySQL default isolation level: REPEATABLE READ

  • Each transaction sees a consistent snapshot
  • Changes are invisible to other transactions until commit
  • Prevents phantom reads and non-repeatable reads
Atomicity Guarantee

All operations within the transaction are atomic:

  1. Lock product rows
  2. Validate stock
  3. Reduce stock
  4. Create order record
  5. Create order items
  6. Update cart status

Either ALL succeed (COMMIT) or ALL fail (ROLLBACK)
